# Обзор бизнес-возможностей и сценарии применения (Business Overview)

🌐 **[English](BUSINESS_OVERVIEW.md)** • **[Русский](BUSINESS_OVERVIEW_RU.md)**

**Async Task Engine** - специализированный отказоустойчивый движок пакетной обработки и автоматизации бэк-офисных операций, спроектированный для снижения расходов на инфраструктуру, защиты баз данных от перегрузок и оптимизации работы служб технической поддержки

---

## 1. Проблемы бизнеса и риски наивных решений

В большинстве растущих компаний пакетные операции (импорт прайс-листов, расчет биллинга, синхронизация складов) начинаются с простых скриптов по расписанию (Cron) или базовых очередей. По мере роста клиентской базы эти решения приводят к трем системным рискам:

```
┌────────────────────────────────────────────────────────────────────────┐
│                      ТИПИЧНЫЕ БИЗНЕС-БОЛИ И УБЫТКИ                     │
├───────────────────────┬────────────────────────┬───────────────────────┤
│    ПАДЕНИЯ СЕРВЕРОВ   │  ФИНАНСОВЫЕ ДУБЛИКАТЫ  │    СЛЕПЫЕ АВАРИИ      │
│     (Out-Of-Memory)   │  (Race Conditions)     │      (Dark Debt)      │
│                       │                        │                       │
│ Загрузка файла на 50k │ Двойной клик менеджера │ Скрипт тихо упал ночью│
│ строк съедает всю RAM,│ списывает деньги дважды│ Клиенты жалуются, а   │
│ OOM Killer роняет API │ База блокируется из-за │ саппорт часами ищет   │
│ и соседние сервисы    │ взаимных блокировок    │ причину в логах по SSH│
└───────────────────────┴────────────────────────┴───────────────────────┘
```

* **Инфраструктурная нестабильность:** Попытка загрузить 100 000 строк в память одним списком вызывает скачок потребления RAM и аварийную остановку контейнера операционной системой (OOM Killer)
* **Повторные финансовые операции и коллизии:** При медленном ответе сети операторы повторно нажимают кнопку в интерфейсе. Без распределенной идемпотентности это приводит к двойным списаниям, дублированию заказов и жалобам клиентов
* **Штрафы и блокировки со стороны внешних API:** Банковские шлюзы, налоговые сервисы и маркетплейсы имеют жесткие квоты (RPS). Залповая отправка запросов приводит к бану IP-адресов компании и остановке отгрузок
* **Высокая стоимость поддержки:** При сбоях инженеры L2/L3 тратят часы на подключение к боевым серверам через SSH, поиск причин в неструктурированных логах и ручные скрипты восстановления

## 2. Ключевые возможности и бизнес-выгода (ROI)

| Возможность платформы | Техническая реализация | Бизнес-выгода для компании |
|---|---|---|
| **Защита от падений по памяти** | Потоковый генераторный чанкинг (`chunk_iterator`) | **Снижение расходов на серверы на 40-60%:** движок стабильно переваривает массивы из сотен тысяч строк при фиксированном лимите оперативной памяти (от 128 MB RAM на контейнер) |
| **Гарантия от двойных списаний** | Атомарный токен `SET NX` в Redis до отправки в брокер | **Нулевой риск финансовых дубликатов:** повторные клики мгновенно распознаются и отсекаются за доли миллисекунды без дублирования нагрузки |
| **Защита внешних контрагентов** | Встроенный Token Bucket ограничитель скорости | **100% защита от штрафов и банов:** напор запросов плавно сглаживается под лимиты банков и партнеров без спам-пиков |
| **Снижение нагрузки на L2/L3 саппорт** | Веб-консоль управления + двухсторонний DLQ Replay | **Экономия до 70% времени дежурных:** саппорт видит стектрейсы ошибок в браузере, запускает повтор упавших задач в один клик и эскалирует тикеты разработчикам без входа на сервер |
| **Безопасность корпоративной сети** | SSRF-фильтрация и криптографическая подпись HMAC-SHA256 | **Защита от утечек и взлома:** внешние вебхуки не могут быть использованы злоумышленниками для сканирования внутренних сетей или облачных метаданных |
| **Изоляция очередей без простоев (Zero-Downtime)** | Топология Topic Exchange с общим пулом (`tasks.general.*`) и выделенными воркерами | **Защита быстрых операций от тяжелых:** тяжелые выгрузки (PDF, ML) изолируются в отдельные воркеры на лету без перезапуска системы, гарантируя стабильный SLA для критических клиентских запросов |

## 3. Индустриальные сценарии применения (Enterprise Use Cases)

### Сценарий 1: FinTech и Необанкинг (Массовый регулярный биллинг)

* **Контекст:** В первый день месяца необходимо списать абонентскую плату с 50 000 лицевых счетов клиентов
* **Проблема:** Если несколько параллельных процессов пытаются списать средства с одного клиента или счета холдинга, возникают дедлоки базы данных и отрицательные балансы
* **Решение движка:**
  * Поле `resource_id` блокирует конкретный счет на время транзакции
  * Токен-бакет регулирует напор запросов к банку на уровне 50 транзакций в секунду
  * При сетевом сбое банка задача уходит в Dead-Letter Queue с сохранением исходного платежного поручения. После восстановления связи саппорт нажимает **Replay**, и система проводит платеж с высоким приоритетом без потери данных

---

### Сценарий 2: E-Commerce и Маркетплейсы (Синхронизация складских остатков)

* **Контекст:** Крупный ритейлер синхронизирует 200 000 складских позиций между 1C, Wildberries, Ozon и собственным интернет-магазином
* **Проблема:** Всплеск заказов в распродажу приводит к тому, что менеджеры запрашивают выгрузку одновременно. Сервер базы данных зависает, сайт перестает открываться
* **Решение движка:**
  * Запросы на экспорт моментально принимаются API со статусом `202 Accepted` и выстраиваются в очередь по приоритету
  * Чанкер нарезает выгрузку порциями по 100 записей и выполняет пакетный `bulk-upsert`, минимизируя время удержания транзакций
  * Менеджеры в реальном времени видят процент выполнения выгрузки в браузере без необходимости обновлять страницу

---

### Сценарий 3: Управление персональными данными (GDPR / 152-ФЗ)

* **Контекст:** Пользователь мобильного приложения запрашивает выгрузку всего архива своих данных («Право на доступ к данным») либо требует удалить профиль («Право на забвение»)
* **Проблема:** Сбор истории заказов, чатов поддержки и логов за 5 лет требует обхода десятков таблиц и занимает до 10 минут. Держать открытое HTTP-соединение невозможно
* **Решение движка:**
  * API регистрирует задачу с уникальным `task_id` и сохраняет обратный `callback_url`
  * Воркер в фоновом режиме собирает ZIP-архив, не блокируя основной Web API
  * По окончании воркер отправляет HMAC-подписанное событие `task.completed` в шлюз уведомлений, и пользователь получает push-сообщение о готовности архива

## 4. Сравнительный анализ с альтернативами

| Критерий | Простые Cron-скрипты | Celery | Apache Kafka | **Async Task Engine** |
|---|---|---|---|---|
| **Порог входа и развертывание** | Минимальный | Средний (сложный конфиг) | Высокий (Zookeeper/KRaft) | **Минимальный (Docker Compose за 30 секунд)** |
| **Изоляция ресурсов (Locking)** | Ручные блокировки в БД | Требует сторонних плагинов | Через партиционирование | **Встроенный Redis-лок по `resource_id` на Lua** |
| **Ограничение скорости (Throttling)** | `sleep()` в коде | Отдельные брокеры | Через consumer lag | **Встроенный внутрипроцессный Token Bucket** |
| **UI-консоль для операторов саппорта** | Отсутствует | Flower (только мониторинг) | Confluent / AKHQ | **Встроенная консоль с Replay и генерацией инцидентов** |
| **Защита от утечек памяти (OOM)** | Нет (весь файл в RAM) | Зависит от разработчика | Через пакеты сообщений | **Встроенная генераторная нарезка (`chunk_iterator`)** |
| **Безопасность вебхуков** | Нет | Нет | Не применимо | **Встроенная защита от SSRF и HMAC-SHA256 подпись** |

## 5. Резюме для технического руководства

**Async Task Engine** занимает нишу между тяжелыми брокерами корпоративного уровня (Kafka) и низкоуровневыми библиотеками фоновых задач (Celery), предоставляя готовое платформенное решение:

* **Для бизнеса:** Защита от простоев, исключение финансовых дубликатов, прозрачность сроков исполнения клиентских задач
* **Для разработки:** Быстрое подключение новых типов задач через чистый паттерн реестра без необходимости настраивать топологию очередей вручную
* **Для поддержки:** Автономная веб-консоль, снижающая эскалации на программистов и позволяющая решать инциденты на первой линии
